## 1. 実装の地図

ヘッダオンリー。`include/krisite/` は外部依存ゼロ。

| ファイル | 責務 | **そこだけが持つ不変条件** |
|---|---|---|
| `config.hpp` | `b` と座標の許容範囲 | `kCoordMin/kCoordMax` が §2 の唯一の定義 |
| `arith/intrinsics.hpp` | 64bit リム演算 3 種 | **経路の切替はここだけ。**上位から見えない |
| `arith/fixed_int.hpp` | 型・符号・幅変換 | `narrow()` が §3 の上界を実行時に守る関所 |
| `arith/ops.hpp` | 四則・比較・行列式 | `mul` が `N+M` リムに必ず収まる |
| `geom/widths.hpp` | ビット幅解析の constexpr 化 | **リム数の数値リテラルはこのファイルだけ** |
| `geom/point.hpp` | `IPoint` / `HPoint` / `Axis` | `HPoint::w != 0` |
| `geom/plane.hpp` | 平面と構成 | 平面は `N·x + d = 0`（`d = -N·p₁`） |
| `geom/predicates.hpp` | 述語 6 種 | 返り値は必ず −1 / 0 / +1 |

述語はすべて `*_value()`（被符号値を返す）と `*()`（符号を返す）の対で持ちます。
§8.4 のビット幅実測が、述語と同じ計算経路の値を測れるようにするためです。
**測定用に式を書き写すと、写し間違いで測定が嘘になります。**

## 2. 設計判断と根拠

### 2.1 リム数の単一情報源

`geom/widths.hpp` の `bits::` / `limbs::` だけがリム数を知っています。他は全部そこから導出。

- **代案**: 各所で `fixed_int<4>` のように書く
- **採らない理由**: `b` を変えたときに追随漏れが起きる。b=26 でのビルドが通るのは
  この一元化のおかげです。実際 §3.3 の改訂（`cmp_h` が 5 リム）で触ったのは
  `widths.hpp` への定数追加と `cmp_h_value` の戻り値型 1 箇所だけで、
  呼び出し側は 1 行も変えていません

### 2.2 `narrow()` を検査付きにした

`resize<M>()` は `M < N` のとき、切り捨てる上位が符号拡張ぶんであることを検査します。

これは単なる安全網ではなく、**§3 のビット幅解析が破れた瞬間に停止する関所**です。
CLAUDE.md が「§3 の理論上界を実測が超えたら即座に報告」と言っている状況を、
`KRISITE_CHECKED_ARITH=ON` のビルドが自動で捕まえます。

- **代案**: リム単位の自然な幅（`mul` の `N+M`）をそのまま持ち回る
- **採らない理由**: 幅が単調に膨らみ、`side` が 5〜6 リムになる。
  §3.3 の表と実装の幅が一致しなくなり、仕様の検算が効かなくなります

### 2.3 `mul` は「符号なし筆算 + 符号補正」

```
a*b ≡ a_u*b_u − (a_u << 64M)[b<0] − (b_u << 64N)[a<0]   (mod 2^(64(N+M)))
```

- **代案**: 絶対値を取って符号を後付け
- **採らない理由**: 最小値の絶対値が同じ幅に収まらず、分岐が要る。上式なら分岐は
  符号ビットの 2 回だけで、`min × min = 2^(64(N+M)−2)` も特別扱いなしに収まります

内側ループの `carry = hi + c1 + c2` が 64bit に収まる根拠はコード中のコメント参照
（128bit の総和が `2^128 − 1` を超えないため）。**ここは筆算実装の定番の落とし穴**です。

### 2.4 行列式は列幅をそろえる — `intersect3` が重い理由

`intersect3` は法線（1 リム）とオフセット（2 リム）が混ざった 3×3 行列式を 4 回計算します。
**全列を最大幅にそろえてから 7 リム幅で計算**しています。

その代償が `intersect3` の **262 ns/op** で、`side` の 7.8 ns に対し突出しています。

- **代案**: 列ごとの幅を保った混合幅 `det3`
- **採らない理由**: SPEC §0「性能より正しさを優先」。数倍は縮むはずですが、
  Phase 0 では手を付けない。**Phase 1 で `side` との呼び出し比率を測ってから判断**

> EMBER の想定では構成点は一度作って何度も `side` にかけるので、
> `intersect3` の重さが支配的になるとは限りません。比率を測る前の最適化は無駄になります。

### 2.5 `side` の累算器を `kSide` リムに詰める

各積を `resize<kSide>` で詰めてから足しています。詰めずに足すと 5〜6 リムになりますが、
§3.1 の `9b+20` と実装の幅が一致しなくなります（2.2 と同じ理由）。

### 2.6 `cmp_h` を `kCmpH` リムに詰める — **実行時コストはゼロ**

リム単位の積は `kHomoW + kHomoXyz + 1` = 7 リムを生みますが、§3 の上界 `13b+27`
（b=21 で 5 リム）へ `resize` で詰めています。上界超過を検査ビルドで捕まえるためです。

**この詰め直しに実行時コストはありません。** `resize` の有無だけを変えた A/B 測定:

| | ns/op |
|---|---:|
| `resize` あり（現行） | 9.66 |
| `resize` なし（7 リムのまま） | 9.67 |

Release（`KRISITE_CHECKED_ARITH=OFF`）では `narrow` は下位リムのコピーに縮み、
符号を取るだけの後段では 5 リムと 7 リムの差が出ません。**外す理由がないので残します。**

> 当初この差を「約 2 ns の代償」と書きかけました。実際には
> ベンチの実行ごとのばらつき（同一条件で 9.0〜11.3 ns、±15% 程度）を
> 原因の違いと取り違えていたものです。**単発の測定値の差に原因を当てない。**

### 2.7 `KRISITE_CHECK` を `NDEBUG` から独立させた

`assert` ではなく専用マクロにしてあります。SPEC §3.4 が
「リリースビルドでも `KRISITE_CHECKED_ARITH=ON` で有効化できること」を要求しているためで、
`assert` は `NDEBUG` で消えてしまいます。

停止処理は `fprintf` + `abort` で、可変な静的状態を持ちません（`arith/` の制約）。

### 2.8 外部テストフレームワークを使わない

各テストは独自 `main` を持ち、非零終了で ctest に伝えます（`tests/test_util.hpp`）。

- **代案**: GoogleTest / Catch2
- **採らない理由**: CLAUDE.md「新しい外部依存を入れる前に必ず確認を求めてください」。
  確認を挟むより 200 行足らずのハーネスで済ませるほうが速い。乱数も `splitmix64` を自前で持ち
  （`std::mt19937` の実装差を避けるため）、同じ種で常に同じ列になります

### 2.9 128bit 正解器を自前で持つ

`tests/int128_oracle.hpp`。**64bit 演算だけ**で書いてあります。

MSVC に `unsigned __int128` が無いため（SPEC §5.3）。乗算は 32bit 部分積を 128bit 加算で
積み上げる形で、本体の「符号なし筆算 + 符号補正」とは別経路を通ります。
**正解器が被検体と同じ道筋を通ると、同じ間違いをして両方が通ってしまいます。**

`__int128` がある処理系では `i128_selfcheck()` が正解器自身を突き合わせます。
MSVC で自己検証は走りませんが、他プラットフォームの CI がその正しさを担保します。

### 2.10 仕様に書かれていない判断

| 箇所 | 判断 | 根拠 |
|---|---|---|
| `orient2d` の投影順序 | X を落とす→`(y,z)`、Y→`(z,x)`、Z→`(x,y)` | 巡回順にすると返る符号が法線の当該成分の符号に一致する |
| `side(plane, IPoint)` の幅 | `max(kNormal+kCoord, kOffset) + 1` リム | 差が `3b+6` になるため。§3.1 の表に無い量 |
| 退化三角形の平面 | `N = 0, d = 0` を返す（エラーにしない） | 呼び出し側が `is_degenerate()` で判定。述語側で分岐を増やさない |
| `cmp_h` の `w1 = w2` 早期脱出 | `cmp(x1,x2) * sign(w1)` | SPEC §7.2 は「x1 と x2 の比較のみ」と書くが `sign(w1)` 倍が要る |

最後の 1 件は仕様の簡略化が不正確な例です。`w < 0` の構成点で符号が反転します。

## 3. 仕様へフィードバックした 3 点（決着済み）

実装中に見つけ、仕様担当が 2026-08 改訂で採用したもの。**すべて解決済み**です。

| # | 内容 | 決着 |
|---|---|---|
| 1 | §2 の座標範囲 `|coord| < 2^b` が §3.1 の表と矛盾 | 符号付き `b` ビットに訂正 |
| 2 | 平面の符号が §3.1（`N·x = d`）と §7.2（`+dw`）で不整合 | 同次 4 元 `N·x + d = 0` に統一 |
| 3 | `cmp_h` のビット幅が表に無い（`13b+27`、5 リム） | §3.1 / §3.3 に追加。**最大幅は `side` ではない** |

改訂後、§3.1 の表に残っていた 4 箇所の編集漏れを、使い捨てのスクリプトで機械的に
修正しました（置換箇所がちょうど 1 つ見つかることを書き換え前に確認する形で）。
うち 1 件（Cramer の置換列が `d` のままだった。正しくは `-d`）は**字義どおり実装すると
符号が反転した点を返す**ので、編集漏れではなく実害のある誤りでした。

## 4. 検証の設計

### 4.1 規模

| テスト | 検証件数 | 何を見るか |
|---|---:|---|
| `fixed_int` | 2,514,793 | 算術の性質。128bit 正解器との突き合わせ + 正解器の自己検証 |
| `predicates` | 847,768 | §8.3 の不変条件。24 置換の符号、スカラー倍不変性、全順序公理 |
| `degenerate` | 442,517 | §8.2 の 8 種を明示的に構成 |
| `bitwidth` | 31 | §8.4。実測ビット幅 vs 理論上界 |
| `fixed_int_gmp` | 115,345,259 | GMP 差分（10^7 組 × 幅 1..4 リム） |
| `predicates_gmp` | 32,514,327 | GMP 差分（10^6 件、うち構成点あり 971,431） |
| **合計** | **約 1.52 億** | |

### 4.2 正解器の独立性

**同じ変形を使う正解器は正解器ではありません。**

| 正解器 | 独立性の担保 |
|---|---|
| GMP（述語） | **有理数（`mpq`）で実座標を復元してから評価。**固定幅側の「`sign(w)` を掛ける」変形を使わないので、変形そのものの誤りも捕まる |
| GMP（平面・構成点） | `mpz` で係数を厳密比較。行列式も独立に余因子展開で書き直し |
| `I128`（算術） | 32bit 部分積を 128bit 加算で積み上げ。本体の符号補正方式とは別経路 |

### 4.3 検出力の実測 — 変異テスト

**テストが本当に効いているかは、壊してみないと分かりません。** 意図的に誤りを埋めて確認した結果:

| 埋めた誤り | 落ちたテスト | 失敗件数 |
|---|---|---:|
| `side` の `d*w` を減算に | predicates / degenerate / predicates_gmp | 73,470 / 28,361 / 15,707 |
| `cmp_h` から `sign(w2)` を落とす | predicates / predicates_gmp | 8,937 / 3,588 |
| `plane_from_triangle` の `neg` を外す | 3 テスト全部 | 43,470 / 44,168 / 51,911 |
| `intersect3` の置換列を `+d` に | 3 テスト全部 | 60,000 / 44,268 / 48,426 |

**4 件とも複数のテストが独立に検出しています。**単一のテストに依存していません。

### 4.4 §8.4 の検査を「硬く」しすぎない

ビット幅実測は 2 つの検査を持ちますが、性質が違います。

- **硬**: 実測 ≤ 理論上界。破れたら設計の誤りなので必ず落とす
- **参考**: 上界が過大でないか。**乱択は真の最大に届かない**ので、リム境界を下回っても落とさない

当初これを「リム数が理論値と一致すること」と硬く書いて偽陽性を出しました（b=21 の
`d` と `side` が 1 リム下に出る）。SPEC §3.4 が後に
「乱択の実測値でリム数を減らさないこと」と明文化したのと同じ話です。

### 5.1 ビット幅（実測 / 理論）

| 量 | b=21 | b=26 |
|---|---|---|
| 法線 `2b+3` | 43 / 45（1 リム） | 53 / 55（1 リム） |
| オフセット `3b+5` | 63 / 68（2 リム） | 78 / 83（2 リム） |
| 構成点 `w` `6b+12` | 129 / 138（3 リム） | 158 / 168（3 リム） |

- `side(plane, HPoint)` = **7.80 ns/op（128 Mops/s）** — 浮動小数点フィルタ要否の判断材料

## 6. つまずいた点（再発防止）

| 症状 | 原因 | 対策 |
|---|---|---|
| ヘッダを直したのに挙動が変わらない | マウントの mtime 粒度が粗く **ninja が再ビルドを取りこぼす** | ヘッダ変更後は `touch` か `--clean-first`。一度これで誤った変異テスト結果を信じかけた |
| `CMakeLists.txt` が壊れた | `clang-format -i` を CMake ファイルにかけた | 対象は `*.hpp` / `*.cpp` に限定する |
| ベンチが 10 分でタイムアウト | 平面の添字写像 `i, 7i+1, 13i+5` が **i=170 で 2 つ衝突**し、その組は絶対に交点を持たず無限ループ | 相異なる添字を明示的に選ぶ |
| MSVC の CI が落ちた | **テストが**正解器に `__int128` を使っていた。ライブラリ本体は無事 | 2.9 の可搬正解器へ |
| `side` のビット幅実測が常に 0 | 構成に使った平面で測っていた（定義上 0） | 別の平面をプローブに使う |
| `bitwidth` テストが偽陽性 | 4.4 参照 | |

**MSVC の件が示唆すること**: SPEC §5.3 は「MSVC には `__int128` が無い」と本体について
警告していましたが、実際に落ちたのはテスト側でした。
**制約はライブラリ本体だけでなく、それを検証するコードにも同じように効きます。**

## 8. 検証環境について

**手元で走らせたのは clang のみです。**GCC / MSVC / Apple Silicon の検証は
`.github/workflows/ci.yml` が唯一の根拠です（SPEC §9）。

開発コンテナには最初コンパイラも CMake も GMP も入っておらず、`sudo apt` も使えませんでした。
`pip` で cmake / ninja、`ziglang` 配布の clang（`zig c++`）、GMP は Ubuntu アーカイブの
`.deb` を `dpkg-deb -x` でホームに展開、という構成で立ち上げています。
**この経緯があるので、手元の数値も「通った」もすべて clang 単独の話です。**

`BENCH.md` の数値は開発コンテナ（AMD Ryzen 7 9800X3D / clang 21 / Release）のもので、
CI ランナーの数値とは比較できません。CI の `bench` ジョブは傾向の監視だけで合否に使いません。

コミット構成について: CLAUDE.md は「テスト追加と実装を分ける」と「テストが通らない状態で
コミットしない」の両方を求めますが、初期導入では**テストは実装なしにコンパイルできない**ため
両立しません。モジュール単位で実装＋その性質テストをひとまとめにし、GMP 差分テストと
退化ケーステストを別コミットに分ける形にしました。PR #1 の 7 コミットのうち、ビルド対象を含む 6 本すべてが単独でビルド・テストを通ることを worktree で確認済みです（残り 1 本は土台のみでビルド対象なし）。
