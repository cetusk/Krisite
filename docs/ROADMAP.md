## Phase 1 が分岐点だった理由

Phase 1 は **この方式を続けるか断念するかを決めるフェーズ**でした。
**判断は続行です**（上記）。以下は、なぜその問いを最初に置いたかの記録です。

この方式で難しいのは論文の中核ではなく**出力抽出**です。並列化のために入力を
セルに分割する以上、**セル境界の継ぎ目**が構造的な弱点になります。同じ幾何点が
複数のセルで独立に計算されるので、それが同一の頂点だと認識されなければ、
そこで割れるか非多様体になります。

そこで Phase 1 では、適応分割・並列化・最適化をすべて外し、**継ぎ目だけを変数として
残した最小構成**で可否を判定します。詳細と中止条件は `SPEC-phase1.md` §11。

### 中止した場合に取る予定だった道（記録）

`csg/` を Manifold（Apache-2.0）のラッパとして実装し、ブール演算のフェーズを飛ばして
点群・メッシュ化へ進む計画でした（**当時のフェーズ番号での Phase 2〜4 / Phase 5 系**。
番号は 2026-08-28 に繰り下がっています）。

**Phase 0 の算術基盤はどちらの分岐でも無駄になりませんでした。** GWN の分類器、
点群の量子化、メッシュ化の述語でそのまま使えます。

### Phase 2 — 適応分割・構成点の保持・意味論の確定

仕様は `SPEC-phase2.md`。**完了条件は正しさのみ。性能目標は設定せず、数値は記録します。**

**中心的な設計問題は分割平面の絞り込みです**（§2）。Phase 1 は大域平面集合を要求して
継ぎ目の整合を保ちましたが、適応分割の目的はセルごとの平面数を減らすことなので、
両者は正面から衝突します。問題は 2 つに分かれます。

| | 対象 | 状況 |
|---|---|---|
| (a) | メッシュ平面 | 「三角形が届くか」ではなく**「平面がセルを横切るか」**で絞れば整合します（§2.3） |
| (b) | **セル面平面** | 適応分割では隣接セルの深さが違うため、細かい側の内部セル面が共有面を分割します。`SPEC-phase1.md` §4.3.1 の「グリッド平面は no-op」は固定深度だから成り立っていた一文です |

**(b) の解法は「縫合後に T 頂点を解決する」です**（§2.4.2、案 D）。グリッド平面を
両側で共有する道は閉じています。§2.3 の基準をセル面平面に当てると整合はしますが、
平面が無限に延びるので遠方の細かいレベルが全体に伝播し、一様グリッドに潰れます。
局所的な規則に弱めると、隣接する葉で分割レベルが一致することが要求され、
葉の隣接グラフが連結なので**大域定数に潰れます。2:1 バランスは救いになりません**
（縛るのは隣接の深さの差であって、木の大域的な深さの幅ではないため）。

制約は Fragment の辺平面列の表現にあり、**縫合後の頂点 ID 列には効きません。**
そこでセルごとの arrangement は自分の 6 面だけで行い、縫合後に T 頂点を入れます。
**挿入する頂点は細かい側が既に作ったものなので、新しい幾何を作りません。**

**あわせてセル割り当てを半開区間 $[\text{lo}, \text{hi})$ に変えます**（§3.4）。
閉領域割り当てでは、セル境界に完全に乗る面が両側に入ります。固定深度では両側の断片が
一致して `region_key` が併合していましたが、**適応分割では粗い側の 1 枚と細かい側の
4 枚が入れ子になり、併合されずに同じ面積が二重に出力されます。** これは案 D とは
無関係で、T 解決では直りません。挙動が変わるのは**境界平面に完全に乗る面だけ**で、
接するだけの三角形は引き続き両側に入ります。

**意味論を変えないので、Phase 1 の固定深度実装がそのまま正解器になります**
（§9.1 分割戦略不変性）。**固定深度モードは消さないでください。**

**最適化の順序が Phase 1 の実測で決まりました。** `side` : `intersect3` の呼び出し比が
**1.26 : 1** で、`intersect3` が述語時間の 94.9%（推定）を占めます。原因は
`split_fragment` が構成点を毎回作り直していることなので、

1. **断片の構成点を保持する**（回数を減らす）
2. `intersect3` の混合幅化（単価を下げる）

の順です。§12 は 2 を挙げていますが、**1 が先**です。詳細は `IMPL-phase1.md` §5.6。

**非多様体出力の意味論**も Phase 2 で確定します（`SPEC-phase2.md` §5）。
**壊れる検査は接触の次元で決まるので、分裂も 2 種類が要ります。**

| 接触 | 壊れる検査 | 操作 | 実測 |
|---|---|---|---|
| 辺（次数 4） | `edge_manifold` | 辺とその端点を分裂 | 11b の $\cup$ |
| 頂点（$k$ 個の扇） | `vertex_manifold` | 頂点を $k$ 分裂 | 4T、4T′ |

**頂点分裂だけでは 11b が直りません**（扇の最大が 1 で、適用対象がない）。
両方を入れて `SPEC-phase1.md` §9.3 の除外 3 件が 0 件になります。
**性能ではなく検査体系を強くする変更です。**

**比較は $(C, \chi)$ で行います。** $g = C - \chi/2$ は $\chi$ が偶数のときにしか
種数を意味せず、非多様体出力では $\chi$ が奇数になり得ます（11b の $\cup$ は $\chi=3$）。

#### 要件の追加 — CSG ツリー（$n$ 項演算）★

**これがフェーズ構成を変えた直接の原因です。**

ブール演算は**複数回連鎖して使われるのが常態**であり、$n$ 項演算として一度に評価できる
必要があります（二項は $n{=}2$ の特殊ケース）。

現在の二項 API では、$(A \cup B) \setminus C$ を計算するのに中間結果を整数へ丸める必要があり、
**そこで厳密性が切れます。** 出力の頂点は構成点（有理数）で、入力は `IPoint`（整数）なので、
型が閉じていません。

**符号ベクトル分類は本質的に二項なので、$n$ 項に拡張できません。** WNV は $\mathbb{Z}^n$
なので自然に $n$ 項です。**要件が分類方式を決めました。**

#### 確定した契約

```
from_mesh : TriMesh(整数) → PolySoup         入口。量子化・凸分割・辺平面の構成
boolean   : PolySoup × … → PolySoup          ★ 【CSG について閉じる】n 項
to_mesh   : PolySoup → TriMesh               出口。縫合・T 解決・再併合・三角形化
```

| | 内容 |
|---|---|
| **公開出力** | **三角メッシュ**（多様体・非多様体の両方）。相互運用の要求 |
| **中間表現** | **凸多角形（平面ベース）を保つ。** CSG について閉じるので丸めなしで連鎖できる |
| 入力 | PWN（自己交差・非多様体・退化を受け入れる）。**開曲面は対象外**（実数値 GWN が要る） |

**平面の枚数は増えますが、各平面の係数は入力のまま**なのでビット幅が伸びません
（OEBSP §3.1「CSG 演算は新しい平面を導入できない」）。

#### 中核から `cmp_h` が消えます

頂点の併合は**縫合するときにしか要りません。** 連鎖では各演算が多角形を切り直すだけなので、
頂点は平面3つ組のままで足ります。共平面重複は多角形の**全順序**で扱えます（EMBER §4.3 C4）。

| | 最大ビット幅 |
|---|---|
| **中核** | **256 を目標**（EMBER と同じ） |
| `to_mesh` | 320（`cmp_h`） |

#### 段階

| 段 | 内容 | 位置 |
|---|---|---|
| **0** | 代表点の構成を平面ベースに戻す（float ヒント + 辺平面オフセット） | **判断を待たず実施可**。487 bit の述語が消える |
| **1** | 葉の閾値の実測、**八分木が 3 軸同時に切る代償の実測** | 同上 |
| **2** | **WNV / WNTV による分類、$n$ 項、局所 BSP** | Phase 3 の本体 |
| **3** | 中核と後処理の分離 | **段 2 の後に、並列化の利得を測って判断** |

段 3 は「出力契約の変更」ではなく**既存機構の移動**です。頂点併合・T 解決・接触の分裂・
三角形化はすべて実装済みで、並列パスの外へ出すだけです。

#### 入口の凸分割 — まず三角形化、次に凸分割

**三角形化を先に実装し、凸分割は後から足して選択できるようにします。**
凸分割は「三角形化してから、凸性が保たれる限り貪欲に併合する」形なので、
**併合の上限を 0 にすれば三角形化**になります。コードは一本化できます。

**比較で答え合わせができます。**

| 量 | 一致するか |
|---|---|
| 体積、$(C, \chi)$ | **厳密に一致** |
| 三角形の集合、断片数、平面数 | **一致しない**（凸分割のほうが少ない。それが目的） |

**切り替えは実行時に。** コンパイル時定数だと同一プロセスで比較できません
（`KRISITE_P1_DEPTH` で踏んだのと同じ問題）。

貪欲な併合は走査順に依存するので、**正準な順序を決めて決定性を保つこと。**

#### 面併合（`SPEC-phase1.md` §3.5）は「必須」から「任意の最適化」へ

§3.5 は「対角辺が 2 平面の交線として表せない」ことを理由に面併合を**必須**とし、
非凸パッチでは停止する設計でした。**辺平面を構成すれば、この理由が消えます。**

$$N_e = N_s \times (p_2 - p_1), \qquad d_e = -N_e \cdot p_1$$

| | 現状（§3.5） | Phase 3 |
|---|---|---|
| 位置づけ | **必須** | **任意の最適化** |
| 隣接情報 | 必須 | 取れるときだけ使う |
| 非凸パッチ | **停止する** | 併合をやめるだけ |

`IMPL-phase1.md` の申し送り「CDT を入れるか仮想平面を与えるかの 2 択」は、
**辺平面の構成という第 3 の解で決着します。**

**代償はビット幅です。** 辺平面を構成すると `side` が $9b{+}20$ から $13b{+}29$ 規模へ
伸びる見込みで、$b{=}26$ で 256 bit を超える可能性があります。
**仕様検討の最初に導出してください。** 結果次第で $b$ の上限が下がります。

#### `to_mesh` での再併合 — 跨いでよい辺は平面の由来から取れる

FARMA §5.4 の coplanar pocket 検出（「交差セグメントでない辺を跨いで領域成長する」）が
そのまま使えます。**Krisite では判定が無料です。**

| 辺の 2 平面 | 由来 | 跨いでよいか |
|---|---|---|
| 両方が同じメッシュ | 元のメッシュの辺 | **よい** |
| 片方が相手メッシュ | 交差曲線 | **いけない** |
| 片方がセル面平面 | **分割の産物** | **よい**（セル境界の痕跡を消せる） |

入口の凸分割と出口の再併合は**同じ機構**です。跨いでよい辺の判定基準が違うだけなので、
一方を作れば他方がほぼ手に入ります。

#### snap rounding

出力を STL / OBJ に書くには浮動小数点へ丸める必要があり、そこで自己交差が入り得ます
（`SPEC-phase1.md` §5 で未解決と記録した問題）。

FARMA §5.6 に実測と実用的な手法があります。

- 素朴に double へ丸めて **85.2%** が有効な複体になる
- 失敗時は **double → single へキャストして再実行**し、新たな交差を解決 → **96%**
- 反復すれば **99.95%**

FARMA §7.1 自身が「パイプラインの最終段が鎖の弱い環」「交点を直接 float で表現しない
すべての手法に共通する制約」と認めています。**Krisite も例外ではありません。**

### Phase 4 — 並列化

work-stealing。**中核が純関数になっていることが前提**です。

> **前提は満たされています**（2026-08-28 判定）。葉の分類が触るデータはすべて不変で、
> 領域を逆順に分類しても幾何の多重集合が一致します（264 / 264。`IMPL-phase3.md` §5）。
>
> **ただし可変な部分（メモ化・カウンタ・出力バッファ）をスレッド局所に保つことが
> 条件です。** 順序非依存の検査は論理的な依存の不在を示すもので、共有によるデータ競合は
> 見ません。**命中率のためにキャッシュを共有した瞬間に競合が入ります。**
未解決のまま並列化すると、非決定的な破損が出て原因追跡が困難になります。
Phase 1 で継ぎ目を先に潰したのと同じ順序です。

EMBER §4.5.4 は「各分割ステップが本質的に純関数になるよう設計した」としています。
**Phase 3 の段 2（参照点の伝播）と段 3（中核と後処理の分離）が、この前提を作ります。**

**Phase 2 が渡すもの。**

| 渡すもの | 中身 |
|---|---|
| 葉の列挙 | 適応分割（`octree/adaptive.hpp`）。深さの差は最大 2 段 |
| 継ぎ目 | 縫合後の T 解決（案 D）。セルごとの arrangement は自分の 6 面だけで閉じます |
| 割り当て | **半開区間**（EMBER §4.2.1 と一致）。同一領域が複数セルに入りません |
| 状態の持ち方 | 構成点キャッシュは呼び出し側が持って引き回します |
| 正解器 | **固定深度モードと単スレッド実装。** 並列化の答え合わせに使えます |

**決定性を要求してください。** 頂点 ID の割り当ては整列後に行えば実行順序に依存しません。
非決定的な破損はデバッグを困難にします。

## CI の方針（2026-08-28 訂正）

**仕様は「何が検証されなければならないか」を定めます。「いつ走らせるか」は定めません。**

> **訂正**: `SPEC-phase1.md` §10.6 と `SPEC-phase2.md` §9.4 は、検査の一覧に
> 「ブロッキング」と書いています。**意図は「フェーズを閉じる前に必ず green であること」
> であって、「全 PR で毎回走ること」ではありませんでした。** 区別を書かなかったため、
> 運用が最も厳しい解釈に固定されていました。

### 段分け

| 段 | いつ | 中身 |
|---|---|---|
| **PR ゲート** | 毎 PR | format + 主要 1 構成（Linux Clang, b=21）の全テスト |
| **影響トリガ** | 該当パスが変わった PR | 変異（`tests/` / `csg/`）、プラットフォーム行列（`arith/` / CMake）、Manifold（意味論に関わる部分） |
| **main ゲート** | main への push | **全ジョブ** |
| **フェーズ完了** | 締めるとき | **全ジョブが green であることを、対象の SHA 付きで記録** |

**フェーズ完了時の要求は緩めません。** `IMPL-phase2.md` §7.13 の形
（「PR #20 の head `5a9e25a` に対する実行で全 19 ジョブが success」）が正です。

### 影響トリガの注意

**依存を過小評価すると「CI は通ったが main で壊れた」が起きます。**
`csg/` の変更が MSVC を壊すのに `arith/` を触っていない、という組合せは普通にあります。

**トリガは広めに取ってください。迷ったら含める。**
**main ゲートが最後の網**です。main が壊れても即座に検出され、原因の PR も明確なので、
この規模では許容できる取引です。

### 変異テストは頻度ではなくトリガで絞ること

67 件の変異が守っているのは、**ライブラリではなくテスト自身の検出力**です。
壊れるのは (i) コーパスが変わった、(ii) 検出器が移動した、(iii) 変異点が消えた、の
いずれかで、**どれもテストとコーパスの変更が原因**です。

**`tests/` と `csg/` が変わらない PR で変異を回しても、何も新しいことは分かりません。**
定期実行より、パスによるトリガのほうが精密です。

### 削減対象は「合計」ではなく「クリティカルパス」で選ぶこと

**並列に走るジョブでは、壁時計は最も遅いジョブで決まります。**
12 秒のジョブを削っても 1 秒も縮みません。**削減効果を足し算で見積もらないこと。**

ただし**同時実行数の上限に当たっている場合は別です。** public リポジトリの標準ランナーは
20 並列が上限なので、ジョブがキューイングしていればジョブ数そのものが効きます。
**run のタイムラインで開始時刻が揃っているか階段状かを見て判断してください。**

### 第三者 GitHub Actions は SHA で固定すること

**CI で使う第三者アクションは、リポジトリの資格情報を持つ文脈で実行されます。**
可変タグ（`@v5` など）は付け替え可能なので、上流が侵害されれば次の実行から
別のコードが走ります。

**コミット SHA で固定してください。**

```yaml
uses: owner/action@<40桁のSHA>  # v5
```

**新しい第三者アクションの追加は、外部依存の追加と同じ扱いです**（`CLAUDE.md`）。
GitHub 純正（`actions/*`）と標準パッケージで組めるなら、そちらを優先してください。

> Manifold を固定コミットで取得し `LICENSE` の実体まで検査している一方で、
> **CI アクションには同じ規律が及んでいませんでした。** 方針に明文が無かったのが原因です。

### 内容は削らないこと

**67 件という数は過剰ではありません。** どれも必要になって足されたもので、
Phase 2 で 2 度「検出器が黙って移動した」ことを捕まえています（§9.3.2、§5.5.1）。

**削るとすれば頻度であって、検査そのものではありません。**

## 通しての約束

各仕様書と実装ノートに散っているものの再掲です。**フェーズをまたいで守る規律です。**

- **リム数の数値リテラルは `geom/widths.hpp` 以外に書かない**
- **乱択の実測値でリム数を減らさない**（真の最大に届かないため）
- **述語を追加するときは、先にビット幅を導出して `widths.hpp` に定数を足す**
- **述語を実装する前に、その述語の差分テストを書く**
- **正解器は被検体と別経路で書く**（同じ変形を使う正解器は正解器ではない）
- **プラットフォーム検証は CI が正。**開発コンテナに GCC / MSVC を入れて代用しない。
  **ただし「CI が正」は「全 PR で回す」を意味しません**（CI の方針を参照）
- **GPL / LGPL のコードを参照・移植しない。**判断に迷ったら実装せず確認を求める
- **対称性の高い入力はバグを構造的に隠す。**軸平行だけのコーパスは、4 平面同時交差・
  クリップの分岐バグ・変異テストの検出力の 3 つを同時に隠していた（Phase 1 の実例）
- **変異テストはコーパスに依存する。**「どのコーパスで検出されるか」を必ずセットで
  指定し、**素通りする組合せも固定する**
- **フォールバック連鎖は最も一般的なものを先に用意する。**狭い十分条件から始めると、
  退化配置でその条件のほうが先に破れる
